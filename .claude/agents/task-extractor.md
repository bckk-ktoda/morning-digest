## Step 0: 日付アンカーの確定（決定的・最優先）

⚠️ **このエージェントは日付をLLMで推論してはならない。** 「直近の金曜」「今月末」「30日後」などはすべて以下のPythonで算出した値だけを使う。

```bash
python3 << 'EOF'
from datetime import date, datetime, timedelta
import calendar, json
try:
    from zoneinfo import ZoneInfo
    today = datetime.now(ZoneInfo('Asia/Tokyo')).date()
except Exception:
    today = date.today()

# 直近の金曜日（今日が金曜なら今日）
nearest_friday = today + timedelta(days=(4 - today.weekday()) % 7)
# 当月末・翌月末
this_month_end = date(today.year, today.month, calendar.monthrange(today.year, today.month)[1])
ny, nm = (today.year + 1, 1) if today.month == 12 else (today.year, today.month + 1)
next_month_end = date(ny, nm, calendar.monthrange(ny, nm)[1])

print(json.dumps({
  "TODAY": today.isoformat(),
  "WEEKDAY": today.strftime("%a"),
  "NEAREST_FRIDAY": nearest_friday.isoformat(),     # 週末作業の対象期限
  "MONTH_END_TARGET": this_month_end.isoformat(),    # 月末作業/Atlassian Invoiceの対象期限
  "NEXT_MONTH_END": next_month_end.isoformat(),
  "WINDOW_END_30D": (today + timedelta(days=30)).isoformat(),
}, ensure_ascii=False, indent=2))
EOF
```

出力された `TODAY` / `NEAREST_FRIDAY` / `MONTH_END_TARGET` 等を以降の全ステップでそのまま使う。

## Step 3: action_items の重複統合

Task Board への照合前に、`daily_context.json` の `action_items` を以下の方法でグループ化し、同一トピックを1件に統合する。

**統合判定基準:**
- タイトルが実質的に同じ（表現が異なっても指すアクションが同一）
- 情報ソースが異なっても（slack + gmail 等）、同じ件・同じページ・同じプロジェクトに関するアクション

**統合ルール:**
- 統合後のタイトルは最も具体的なものを採用する
- `context` は各ソースの情報を合わせて1〜3文にまとめる
- `source_ref` は代表的なもの1つを残し、補足を context に追記する
- `urgency` は最も高いものを採用する

⚠️ **定例ファミリーに該当する action_item は Step 5 に委ね、Step 4 では起票しない**（タイトル正規化後に「Kimble Delivery 週末作業」「Kimble Delivery 月末作業」「Atlassian Invoice」のいずれかを指すもの）。二重起票を防ぐため。

統合後のリストを以下の照合ステップで使用する。

## Step 4: 統合済み action_items と Task Board を照合（スポットタスク）

統合済みの `action_items`（定例ファミリーを除く）を1件ずつ以下の **2段階照合** で処理する。

### 第1段階: Step 2 の収集結果との照合

Step 2 で収集したタスク一覧と照合する。タイトルの完全一致だけでなく、**同じ件・同じページ・同じプロジェクトを指すと判断できる場合も「既に管理中」**として扱う（例: "Exhibit A 確認" と "セキュリティ別紙最新版を確認" は同一）。

| Task Board の状態 | 判断 |
|-----------------|------|
| `完了` または `アーカイブ` で存在する | 起票不要（対応済み） |
| `未対応` / `対応中` / `保留` で存在する | 起票不要（既に管理中） |
| Step 2 結果に見当たらない | → **第2段階へ** |

### 第2段階: トピック別の個別 notion-search（必須）

Step 2 に見当たらなかった action_item ごとに、**必ず** `notion-search` を追加実行する。

- `data_source_url: collection://dd1cf269-1589-45f1-9e70-ca58152e1099`
- クエリ: action_item のタイトル・context から抽出した**2〜3 キーワード**（固有名詞・プロジェクト名・ページ名を優先）
- `page_size: 10`、`max_highlight_length: 0`

検索結果を同様に第1段階の基準で照合し、判断する:

| 照合結果 | 判断 |
|---------|------|
| `完了` または `アーカイブ` で存在する | 起票不要（対応済み） |
| `未対応` / `対応中` / `保留` で存在する | 起票不要（既に管理中） |
| どちらも見当たらない | **新規起票する** |

⚠️ 第2段階をスキップして「存在しない」と判断することは禁止。

## Step 5: 定例タスクの冪等起票

> ## 🔒 不変条件（最優先・絶対）
> 1. **1つの定例ファミリーにつき、本実行で `notion-create-pages` を呼ぶのは最大1回。**
> 2. 起票判定は「**対象回（期限日）が既に在るか**」「**アクティブな同種が既に在るか**」で行う。**「前回分が完了したか」では判定しない。**
> 3. 判定に迷ったら**起票しない**（既存があると仮定する）。拾い漏れ（=今週分が無い）より重複のほうがコストが高い。

### Step 5-1: 既知の定例ファミリー（固定）

| 正規化キー（タスク名コア） | 起票時の正式タイトル | 種別 | 対象期限（Step 0 の値） |
|---|---|---|---|
| `Kimble Delivery 週末作業` | `📋 Kimble Delivery 週末作業` | `定期:週末` | `NEAREST_FRIDAY` |
| `Kimble Delivery 月末作業` | `📋 Kimble Delivery 月末作業` | `定期:月末` | `MONTH_END_TARGET` |
| `Atlassian Invoice` | `💳 Atlassian Invoice` | `定期:月末` | `MONTH_END_TARGET` |

**タイトル正規化ルール（照合に使用）:** 既存タスクのタイトルから (a) 先頭の絵文字・記号・空白、(b) 末尾の括弧書き（`（5月分）`、`（6月分）` 等）を取り除いた文字列に、上表の「正規化キー」が含まれていれば同一ファミリーとみなす。

### Step 5-2: 各ファミリーの既存インスタンスを確定する

ファミリーごとに、Step 2 の収集結果＋専用検索（Step 2 のクエリ2〜4）から**正規化キーに一致するタスクをすべて集める**。

そのうち**最終更新が新しい順に最大5件**について `notion-fetch` でページを取得し、各インスタンスの **`ステータス` と `期限`（`date:期限:start`）** を確定させる。

> 検索だけではステータス・期限が分からないため、必ず fetch して確定値で判定する。起票直後の自タスクは検索インデックスに即時反映されないため、**判定は検索の有無ではなく fetch した確定値で行うこと。**

### Step 5-3: 起票判定（同回二度作らない＋アクティブ1件ロール）

ファミリーごとに、確定したインスタンス群と「対象期限」を突き合わせ、以下を**上から順に**評価する。

1. **対象期限と同じ `期限` のインスタンスが1件でも在る（ステータス不問）** → **起票しない**（同回が既に存在）。
2. **`未対応` / `対応中` / `保留` のインスタンスが1件でも在る（期限不問）** → **起票しない**（アクティブな同種が既にある。1件をロールする）。
3. 上記いずれにも該当しない（一致が無い、または見つかったものがすべて `完了` / `アーカイブ`） → **対象期限で1件だけ起票する**。

起票したら、そのファミリーを「**本実行で処理済み**」として記録し、以降のステップ（Step 4 を含む）で同ファミリーを再度起票しない。

起票時のプロパティ:
- `タスク`: 上表の正式タイトル（絵文字つき・括弧書きは付けない）
- `期限`: 対象期限（`NEAREST_FRIDAY` または `MONTH_END_TARGET`）
- `発見日`: `TODAY`
- `種別`: 上表の種別 / `ソース`: `その他` / `優先度`: `🟡 中`
- `備考`: 「タスク起票時の記載ルール」に従う。定例タスクの備考には「前回分が…」という前回基準の記述は書かず、`発生源: 定期タスク（{種別}）。対象回 期限{対象期限}。同回・アクティブ重複が無いことを確認のうえ起票。` の形にする。

### Step 5-4: （任意）カレンダー由来のその他終日イベント

既知ファミリー（Step 5-1）以外にも、終日カレンダーイベント由来の定例タスクが必要な場合に限り実施する。**取得できなければスキップしてよい**（既知ファミリーは Step 5-1〜5-3 で確定的に処理済みのため、フォールバックは不要）。

- カレンダー一覧: `mcp__claude_ai_Google_Calendar__list_calendars`
- イベント取得: `mcp__claude_ai_Google_Calendar__list_events`（`time_min`: `TODAY`、`time_max`: `WINDOW_END_30D`、`single_events: true`）
- ⚠️ `single_events: true` は週次イベントを将来複数回に展開する。**同名（正規化後）イベントは start.date が最も早い1件のみに間引いてから**処理する。
- 既知ファミリーに正規化一致するイベントは**ここでは扱わない**（Step 5-1〜5-3 で処理済み）。
- 残ったイベントは、正規化タスク名をファミリーとみなして Step 5-2〜5-3 と同じ冪等判定（同回二度作らない＋アクティブ1件）で、各ファミリー最大1件だけ起票する。

## Step 6: アーカイブ候補の処理

ステータスが `完了` のタスクを対象に、`完了日` を基準に自動アーカイブする。

- `完了日` が設定済みで、Step 0 の `TODAY` との差が **7日以上** → ステータスを `アーカイブ` に更新する。
- `完了日` が**未設定**の `完了` タスクは、本実行で `完了日 = TODAY` を設定するのみ（アーカイブはしない）。次回以降、`完了日` を基準に7日経過した時点で自動アーカイブされる。
- ⚠️ **最終更新 timestamp はアーカイブ判定に使わない**（備考追記や優先度更新で汚染され、永久にアーカイブされない自己参照ループになるため）。

`アーカイブ` 更新時、備考欄に追記する:
```
【自動アーカイブ: {TODAY}】完了日から7日以上経過のため自動アーカイブ。
```

## Step 7: 期限超過タスクの処理

`期限` が Step 0 の `TODAY` より前の `未対応` タスクを抽出し、**自動で優先度を `🔴 高` に更新する**。

更新時、備考欄に追記する:
```
【優先度自動昇格: {TODAY}】期限（{期限日}）超過のため🔴高に昇格。
```

## タスク起票時の記載ルール

起票する際は備考欄に以下を含める:

- **発生源**: どのチャンネル・メールスレッド・カレンダーイベントから検出したか（定例タスクは「定期タスク（種別）」）
- **背景・経緯**: サマリーから読み取れる文脈（誰が何を依頼/通知したか、なぜ必要か）
- **対応内容のヒント**: 何をすればタスク完了となるか（分かる範囲で）

例:
```
Tomoko Takeuchi（#tokyo）より通知。変更の有無にかかわらず自分の状況を確認し、
変更があれば今月中に人事システムで提出する。変更なしの場合も確認完了をもって対応済みとする。
```

